BankTracker

Recruiting timelines are forecastable. The point of forecasting them is to have the networking already done.

Python · JSON state · Google Calendar · scheduled agent github.com/derrla4-beep/BankTracker

The insight

Banks post applications on a highly predictable annual rhythm. The same firm opens the same program within a fairly narrow window year after year, which means a database of historical open dates per firm-program produces a usable forecast of the next one.

That forecast is only interesting because of what it is for. By the time an application goes live, the people who will do well have already spoken to someone at the firm. So the system does not alert on the posting. It alerts at T−4 weeks and T−1 week, when there is still time to have the conversations, and then again on the day so nothing is missed.

The rule that makes it correct

This is the part of the project I would actually want to be asked about, because it is domain reasoning rather than code, and getting it wrong makes every other part of the system useless.

A firm having a live Summer Analyst posting does not mean my program opened. Liveness alone never justifies marking something open. The test is whether the posting’s own stated eligibility includes my graduating class.

Banks recruit roughly eighteen months ahead. In mid-2026 the postings going live are “2027 Summer Analyst” — which are for 2028 graduates. For a 2029 grad those are a year early and not applicable, however live they look. The cycle that matters opens roughly a year after them. A naive tracker fires on every live posting and becomes noise within a week.

But the same rule applied everywhere would be equally wrong in the other direction. Corporate finance and data science run six to twelve months ahead, not eighteen, so for those tracks a Summer 2027 posting is the sophomore-summer role and is applicable. Sophomores are genuinely hired into those, unlike banking where sophomore year is insight programs only. Applying the cycle-ahead rule to a non-banking posting would reject every posting actually available.

Investment banking~18 monthsAppliesPrediction from history
Corporate finance6–12 monthsDoes not applyDetection
Data science6–12 monthsDoes not applyDetection

There is a matching rule for how eligibility gets read. Banks name class years explicitly; corporate and tech postings usually do not. So the requirement is satisfied by any one of an explicit class-year list, a graduation-date window containing the target month, or a class-standing phrase like “rising junior” that maps to a graduation year — and whichever one is found gets quoted verbatim into the record. A posting that says nothing at all about eligibility is never promoted; it is filed as an open question for a human. Not classifiable is a state, not a default.

Why there is no database

No app server, no ORM, no hosted anything. Four plain JSON files in the repository hold all state, read and updated by a scheduled agent that runs Monday, Wednesday and Friday around 8am Eastern.

FileHolds
data/firms.jsonFirm identity, tier, careers URL, insight-program page
data/programs.jsonOne row per firm-program: type, historical open dates, predicted date, confidence, status
data/bu-events.jsonCampus events relevant to recruiting, with source URLs
state/calendar-sync.jsonProgram and event id → the calendar event ids it created

At 115 rows a database would be pure overhead. What I get instead is that the entire state of the system is diffable and reviewable in git: I can see exactly what a run changed, and revert it, without a migration or an admin panel. The tradeoff is real and I would not make the same call at ten thousand rows — there is no concurrency story here and there does not need to be, because exactly one scheduled run touches these files at a time.

Idempotency is the whole reason the fourth file exists

state/calendar-sync.json maps each program id to the calendar event ids already created for it. Without it, every run would happily create a second T−4 alert, then a third. With it, a run that has seen a program before updates the event it already made. Re-running the agent is safe, which means a failed run can simply be run again — the property that makes a scheduled job something you can leave alone.

The validator

Every task in this project runs a validator before considering itself done. It checks all four state files against a written schema contract:

  • Referential integrity — every program points at a firm id that actually exists
  • Enum values — tier is one of the tiers, type is one of the types, status is one of the statuses
  • Date formats — ISO, in a single declared timezone
  • Id uniqueness across every file

It exits 0 with a one-line summary or exits 1 and prints one message per problem. It has its own test suite, written against the standard library only so it runs anywhere with a Python install and no setup.

That is a lot of ceremony for four JSON files, and it is the point. The agent writing those files is a language model, and a language model will occasionally produce a plausible-looking row pointing at a firm that does not exist. The validator is the boundary where that stops being possible. The same instinct shows up in outreach-engine, where post-generation checks are deterministic rather than another model call, and in the batch research pipeline, where nothing enters the tracker unvalidated.

Honest limitations

  • A prediction is a prediction. Firms move their calendars. The confidence field exists because some of these forecasts are built on two data points, and a weekly sweep re-validates stale ones rather than trusting them indefinitely.
  • Firm coverage was seeded narrowly on purpose for the non-banking tracks, and is still expanding. Comprehensive coverage on day one was an explicit non-goal.
  • Detection depends on career pages staying readable. A site that blocks automated reads leaves its program unverified, and unverified is recorded as unverified rather than resolved by assumption.
