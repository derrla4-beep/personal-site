The problem

Mass-templated outreach gets ignored, and writing genuinely specific emails one at a time does not scale past about ten people. The interesting constraint is that personalization is the whole point — so the system cannot simply generate more text faster. It has to force each message to be anchored to a real, verifiable fact about one person, and refuse to send anything that degrades into “I came across your profile.”

Most of the engineering here is that refusal: a rigid output format, a tiered rule for what counts as a real research hook, a validator that rejects filler, and a follow-up state machine that stops rather than nags.

Architecture

Four decisions I would defend

1. Nothing sends when it is written. It sends when the recipient will read it.

Messages queue and release on the next Tuesday, Wednesday or Thursday between 8:30 and 9:59 AM in the recipient’s local timezone. Monday morning competes with the weekend backlog and Friday afternoon gets read and forgotten, so both are excluded deliberately. The minute inside the window is randomized, because a queue that fires every message at exactly 9:00:00 has an obvious machine signature and recipients who compare notes notice.

What it costs: latency. A message written on Friday night sits for four days. That is the right trade when the reply rate on a cold email is a couple of percent and arrival time is one of the few levers that does not require better writing. The timezone itself is inferred from a free-text location string and falls back to US Eastern, which silently mis-times mail to anyone whose location is written unusually.

2. The follow-up machine is built to give up.

Two cases, deliberately asymmetric. No reply at all: up to two follow-ups, then it stops permanently. They replied, you replied, they went quiet: exactly one follow-up, ever, never escalated to a second.

The asymmetry is the entire point. Silence after a first cold email carries no information — they may not have seen it. Silence after a real exchange usually means “not now,” and a second nudge there converts a neutral contact into an annoyed one. There is also a staleness floor: past three weeks a follow-up reads as strange rather than persistent, so those threads are dropped instead of revived.

What it costs: conversions I will never see. Some of those dropped threads would have replied to a third touch. I would rather lose those than be the person whose name in an inbox means another email is coming.

3. Validation is deterministic, not another model call.

Two things run after generation and neither is an LLM. The validator enforces the numeric and structural constraints a model does not reliably self-police from prose — a 100-word cap on the body, 35 words per line, and a single-ask check on the closing line that rejects both multiple question marks and two questions joined by “and.” Then a deterministic pass normalizes punctuation: em dashes become commas, arrows become words, and numeric grouping like 1,000 is protected from the comma normalizer.

Both could have been “ask the model to check its work.” Neither is, for the same reason: the failures being caught are exactly the failures a model is prone to, so asking the same class of system to catch them is unreliable and costs another round trip. A regex that removes every em dash removes every em dash.

The same instinct, one layer up: the generator parses model output by brace-matching every top-level JSON span and taking the last valid one, rather than the first {. When a model second-guesses itself and emits a draft, some commentary, then a corrected blob, naive parsing picks the wrong one.

4. Identity is configuration, not source.

No .py file in the repository names me. The sender’s name, email, school, differentiators and credibility hooks all load from a config file. This started as a privacy requirement and turned out to be the right factoring anyway — the prompt builder is now reusable by anyone, and nothing in the pipeline is actually finance-specific. The voice, the hooks and the sender identity are all data.

The data question

This tool operates on a list of real people who never agreed to appear in a public repository: their names, employers, profiles, work email addresses, and private notes about how to approach them. That data is genuinely useful to the tool and genuinely inappropriate to publish. That constraint, not aesthetics, is what shaped the repository layout.

RuleHow it is enforced
Real data never enters version controlContacts, queue, reply state, processed URLs, tone samples and every PDF, DOCX and XLSX are gitignored
Every committed data file is syntheticInvented people at invented firms on example.com domains
Reads fall back, writes do notA read returns the real file if it exists and the committed example otherwise, so a fresh clone runs end to end. Writes always target the real filename, so example data is never mutated into a mixture of fake and real records.

The failure mode being designed against is the ordinary one: someone clones the repo, runs it, and accidentally commits their contact list. Making the ignored path the default path is what prevents that, rather than a warning in a README.

What it does not do

These are real limitations, listed because a system described only by its strengths has not been examined.

  • No reply ground truth. Status tracking records what was sent, not what actually got a response — so the system cannot learn which hooks work. The prompt encodes cold-outreach best practice, not measured results from this pipeline. Closing that loop is the single highest-value next change.
  • Timezone inference is a keyword heuristic. It reads a free-text location string and will be wrong for anyone who lists a headquarters rather than where they sit.
  • The review UI has no auth. It binds to localhost and assumes a single trusted operator. It should not be exposed to a network as written.
  • Scraping is the fragile tier and is treated as such. CSV is the default path because it always works; the browser-driven path breaks whenever the site changes markup or decides the session looks automated. A pipeline whose first step is the fragile one fails constantly.
